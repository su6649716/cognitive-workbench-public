# 多项目下注复盘

## 目的

让新增项目的机会成本、停滞项目和探索出口可见。不是生成任务清单，也不根据 Agent 活动记录假装知道真实经营投入。

## 信息来源

优先使用：

- 用户明确提供的项目状态；
- 最近的 Agent 任务记录与项目文件；
- 已记录的决定、实验和到期结果；
- 可验证的交付物与变更。

把线程数、文件数、修改频率标为“活动代理”，不能直接翻译成工时、价值或进度。

## 操作

1. 合并同一项目的不同任务名称。
2. 区分主业务、正在验证、维护修复、内容生产、临时探索和长期停滞。
3. 找出有活动但缺少结果证据的项目。
   - 先用 `cognitive_ledger.py audit` 找未关联任务、缺少回看点和重复事件。
   - 用 `project_index.py list` 合并中文名、代码目录名和不同任务标题指向的同一项目。
4. 找出新增项目将挤占的最佳替代项。
5. 对每个候选只提出继续、暂停、结束或保持观察，不代替用户决定。
6. 最多要求用户回答三个取舍问题。
7. 不把“有 task_close 记录”直接等同于项目已交付；代码项目还要核对提交和工程收口状态。

## 资源冲突识别

8. 标出争用同一稀缺资源的项目：用户本人时间、同一批开发/Agent 并发数、同一个发布窗口、同一笔预算。
9. 对每处冲突写一句话：谁让路、让到什么时候、让路期间的最小维持动作是什么。不写"都重要"。
10. 长期停滞 + 无人认领的项目，先标"待决定"而不是直接判死刑——判死刑是用户的决定，不是复盘的决定。

## 回看点

复盘结束时必须留下次回看条件，写入 `portfolio_review` 事件的 `metadata`：

- 时间型："两周后回看长期停滞清单"；
- 事件型："新增项目立项时重跑一次本复盘"；
- 触发型："任一'正在验证'项目出结果后回看"。

没有回看点的复盘等于没做——下次从零开始问同样的问题。

## 输出

```text
本周主攻：
正在验证：
维护与修复：
临时探索：
长期停滞：
证据缺口：

需要用户决定：
1.
2.
3.
```

## 记录

用户确认取舍后记录 `portfolio_review`，并把项目级继续、暂停、结束决定放入 `metadata`。未经确认不修改项目、归档任务或关闭自动化。
