# 认知事件生命周期

## 三个层级

- **请求**：用户的一次表达，例如“再用一次 Skill 重新设计”。
- **事件**：一次改变行动的认知动作，例如扩张判断、假设测试或任务收口。
- **阶段（episode）**：围绕同一真实问题发生的一组关联事件。

请求可以重复，事件不应因此重复。一个阶段可以依次包含 `expansion_gate`、`hypothesis` 和 `task_close`。

## 新建还是续接

新建事件前，按项目和当前任务查询近期账本。依次判断：

1. 真实问题、目标和关键约束是否相同；
2. 是否出现会改变判断的新事实；
3. 用户是否作出新的范围决定；
4. 测试是否正式开始或结果是否返回；
5. 是否形成新的跨任务可复用结论。

只有 2–5 任一项成立，才可能产生新事件或更新。只是换表达、要求第二稿、继续执行既定方案，不新建事件。

## 阶段转移

```text
expansion_gate
  ├─ 用户暂缓/取消 → 更新并关闭
  ├─ 用户直接建设 → 更新选择；实施结果回来后关闭
  └─ 用户开始验证 → 关闭范围判断，并新建关联 hypothesis

hypothesis
  ├─ 测试进行中 → 更新状态或追加说明
  ├─ 结果返回 → 更新为 supported / refuted / inconclusive
  └─ 形成长期决定 → 后续新建关联 task_close

task_close
  └─ 同一决定只保存一次；后续改稿或执行进展不重复收口
```

每次用户可见输出只展示当前阶段最相关的一种工作流。事件可以在后续轮次转换，不要在一张卡里混写三种记录类型。

## 关联规则

- 新阶段首个事件：`episode_id` 默认使用自己的事件 ID。
- 后续关联事件：使用相同 `episode_id`，并把直接上游事件写入 `parent_id`。
- 旧事件没有 `episode_id` 时，查询结果默认把该事件 ID 当作阶段 ID。
- 当前任务 ID 可取得时必须写入 `thread_id`；不可取得时保留来源路径或任务标题，不虚构 ID。
- 新事件未写 `thread_id` 时必须记录无法取得的原因；不能把空值当作正常状态。
- `hypothesis` 必须带日历时间或结果触发条件，保证未来知道何时回看。

## 写入前机械检查

先运行相关项目/阶段查询，再决定 `record` 或 `update`：

- 同一 `episode_id` 已有 `expansion_gate`、`task_close` 或 `portfolio_review`：更新原事件。
- 同一阶段已有 `open/active` 假设：先更新或解决原假设，不能并行制造同义测试。
- 新事实只改变原决定的证据、实现状态或验证结果：更新原事件。
- 只有真实问题改变、开始新的可区分测试或形成不同的长期决定时，才新建事件。

定期运行 `scripts/cognitive_ledger.py audit`。历史缺口只报告，不为了账面整齐而猜测补写。

旧账本已经存在的同阶段重复事件不删除、不覆盖。确认它们确属旧规则遗留后，在非主事件的 `metadata.lifecycle_migration.legacy_duplicate_of` 中指向保留的主事件；审计会继续展示这段历史，但不把已确认迁移视为当前故障。

## 用户决定与系统建议

- 用户明确选择、批准或已经实际执行：可记录为用户决定。
- 系统提出但用户尚未接受的阈值、期限或方案：标为 `proposed`，状态保持 `open`。
- “继续设计”不等于接受所有建议；只记录用户真正确认的部分。
