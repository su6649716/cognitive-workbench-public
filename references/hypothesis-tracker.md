# 假设追踪

## 目的

把即将驱动行动的不确定判断转成可区分结果的现实测试，避免把“试试看”变成无归因修改。

## 合格假设

合格事件必须具有：

- 一个已经观察到的事实；
- 一个尚未确认的解释或预测；
- 一个准备采取的动作；
- 一个未来可以观察的结果。

只有观点、没有行动，或只有动作、没有可观察结果时，不建立追踪。

## 操作

1. 分开写观察、解释和预测。
2. 明确本次只改变什么；若同时改变多个变量，标注无法单独归因。
3. 选择能区分不同解释的证据，不用“感觉更好”作为唯一指标。
4. 约定自然检查点：能确定日期时写 `due_at`；不能确定日期时写一个可观察的 `review_trigger`，例如“首个真实样本完成并收到用户反馈后”。二者不能同时为空。
5. 写出支持、反驳和证据不足三种结果。
6. 到期后先对照原预测，再看实际结果，避免事后改写原判断。

## 输出

```text
观察：
假设：
本次动作：
预测结果：
支持条件：
反驳条件：
检查时间：
回看触发条件：
```

结果回流时追加：

```text
实际结果：
结论：支持 / 反驳 / 证据不足
归因边界：
下一步：
```

## 记录

当用户明确开始测试，或接受系统的一次轻提示后，记录 `hypothesis` 事件。结果回来时使用 `update` 追加，不覆盖原始预测。

脚本会拒绝没有 `due_at` 和 `review_trigger` 的新假设。测试尚未开始但值得保留时使用 `open`，并把开始条件写为 `review_trigger`；正式行动后再更新为 `active`。

若假设来自扩张检查，沿用其 `episode_id` 并写入 `parent_id`。系统提出但用户尚未接受、现实动作尚未开始的测试只能保持 `open`，不能标成 `active`。同一测试的进度只更新原事件；结果形成长期决定时，再在后续建立关联的 `task_close`。
