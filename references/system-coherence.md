# 系统一致性与目的规划：广思考，窄执行

## 目的

当新建或改造系统、产品、工具时，不把用户刚提到的局部需求直接翻译成代码。先恢复用户最终想改变的现实，明确当前交付物在其中只负责哪一段，再规划连续使用路径、必要承接和系统联动，最后把设计范围与本轮实施范围分开。

本分支首先是目的驱动规划，其次才是系统关系扫描。父系统目标不能代替当前组件职责：一个工具服务于“快速上架”，不等于它必须承担上传、图片管理和发布任务；一个学习工具服务于“学会课程”，也不等于它应展示课程原话，而可能需要把知识转成连续操作。

这不是第五个工作流，而是 `expansion_gate` 在既有系统变更场景中的一个分支。

## 触发信号

满足任意一项时进入本分支：

- 既有系统新增模块、页面、字段、状态、角色、权限或数据源；
- 一个局部变化同时影响角色、配置、数据、状态、视图、协议或历史数据中的三层以上；
- 一个任务横跨多个仓库、应用或业务组件；
- 用户要求“形成闭环”“上下联动”“保持原来的设计逻辑”或“主动多想一点”；
- 当前实现虽然满足字面需求，却可能产生孤立配置、孤立表单、孤立指标或无人承接的数据。
- 用户反复纠正产品形态、组件边界、业务规则、操作连贯性、界面可用性或完成标准；
- 已经知道“要做什么”，但还没有把目的推导成完整计划、使用路径和交付形态。

纯机械修改、独立文案调整和不改变业务语义的小修不进入本分支。

## 先恢复规划主线

先从当前原话、历史纠正、项目索引和真实结果中恢复下面六项。它是一条规划主线，不是让用户填写的表单：

```text
最终要改变的现实：用户完成这件事后，现实工作发生什么变化
当前交付物负责：它在整个目标中必须完成哪一段
当前交付物不负责：相邻但不应被吞进来的任务
必须尊重的真实规则：事实真源、不可变数据、计算与业务口径
连续使用路径：用户从什么输入开始，经过哪些动作，到什么结果结束
完成证据：什么可观察结果证明它真的有用
```

特别检查三类常见错位：

- **结果与载体错位**：把“帮助学会操作”做成内容展示，把“提高生产稳定性”做成单点报错修复；
- **父目标与组件错位**：因为最终要上架，就把上架全流程塞进成本表；
- **规则与对象错位**：把只适用于产品成本的涨幅误加到快递费和包装费，或把单价误当成整组价格。

缺失项先从已有事实合理推断并标明来源；系统推断只能作为建议，不是用户目的。只有不同答案会改变产品路线、数据口径或不可逆实现时，才向用户提问；把 1～3 个相关分叉合并提出并给推荐，不逐句索取背景。

形成稳定决定后，用 `scripts/project_index.py upsert --planning-baseline-json <JSON>` 保存紧凑版本，建议字段为 `ultimate_outcome`、`component_job`、`out_of_scope`、`invariants`、`task_path` 和 `success_evidence`，并记录 `purpose_status`、`boundary_status`、`design_status`、`sample_status`、`baseline_status` 与 `baseline_source`。未确认猜测可以临时标成 `assistant_inferred` 或 `draft`，但不能作为中高风险完整实施依据。新任务命中项目时先恢复并核对这份基线是否仍为 `current`。

## 再恢复设计宪法

按以下优先级取得最小充分背景，不要求用户重填需求：

1. 当前用户原话、明确纠正与已确认边界；
2. 父系统的 `PRODUCT.md`、产品原则、业务协议与关键设计文档；
3. 项目索引中的父系统、组件角色、上下游与事实真源；
4. 当前实现、真实数据结构、权限与已有结果；
5. 相关历史任务中的稳定决定。

如果文档与现实实现冲突，把冲突显式列为待决定项；不要默认为文档或代码任何一方天然正确。

恢复基线时同时检查来源和新鲜度：当前用户纠正 > 当前真实结果 > 旧项目基线。事实真源变化、实现与基线冲突、用户否定旧路线时，把 `baseline_status` 标为 `stale` 或 `superseded`，只重开受影响的设计层，不让旧确认继续驱动开发。

先用一句话分别回答：

- 用户为什么做这件事，最终要改变哪项现实工作；
- 父系统最终帮助谁完成什么经营动作？
- 当前组件在父系统里负责生产事实、加工事实、汇总观察，还是执行动作；它明确不负责什么？
- 哪个组件或外部系统是每类关键事实的真源？
- 本次局部需求改变了哪条业务链路，而不只是改了哪个页面？

## 主动向前规划

围绕当前交付物向前推演到用户完成后的直接下一步，但不自动建设下游：

1. **现在必须解决**：缺少就会使当前交付物无法完成职责，进入设计和实施；
2. **现在准备承接**：当前只需提供稳定输出、状态或接口，供下一步使用，不把下游功能塞进来；
3. **未来候选**：有潜在价值但当前没有证据，只记录，不实施。

每个主动提出的功能都要能回答“为什么是当前职责成立的必要条件”。答不出来的内容降为承接准备或未来候选。

## 纠正传播

用户纠正不是孤立需求。先判断它改变了哪一层：

```text
最终目的 / 当前职责与边界 / 真实规则
连续操作路径 / 交付形态与界面 / 完成与验证标准
```

然后执行四个动作：

1. 更新规划主线中的对应项，保留纠正来源；
2. 明确删除或降级被否定的旧路线，不能让旧假设继续残留在页面、数据结构或测试里；
3. 扫描受影响的对象、公式、状态、页面、文档、测试和验收；
4. 继续原任务时只实施修正后仍然必要的范围。

如果用户说“再启动一次认知助手”但没有新事实，续接原规划；如果带来了上述任一层的新纠正，做一次传播更新，不从零重建项目。

纠正若改变目的、职责、产品形态、业务规则、操作路径或验收，属于语义变化：即使代码已经开始，也要暂停继续扩大完整版本，回到设计确认。只涉及库选择、兼容性、性能或测试实现且不改变用户可见语义时，由助手自行处理和验证。

## 双向扫描

### 横向角色闭环

沿同一业务时点检查：

- 谁配置规则或基础资料；
- 谁录入、执行或修正；
- 谁拥有客户、任务或结果；
- 谁查看个人结果；
- 谁做管理判断、纠偏与复盘；
- 不同角色是否看到同一事实的合适切面，而不是复制同一页面。

### 纵向数据闭环

沿事实生命周期检查：

```text
配置/主数据 → 一线输入 → 归属与状态 → 业务结果
→ 个人视图 → 管理视图 → 下游观测/报告 → 复盘与纠正
```

至少扫描这些传播层；只展开与本次需求有关的层：

- 主数据与配置生命周期：新增、停用、删除、历史引用；
- 角色、权限与可见范围；
- 录入入口、移动端与批量导入；
- 领域对象、状态流转与时间语义；
- 所有权、来源与业绩归因；
- 个人工作视图与个人结果；
- 管理汇总、异常与纠偏动作；
- 下游协议、报表和观测口径；
- 历史数据、迁移、未知值与人工修正。

## 主动扩展分级

发现的联动必须分为三层，不得混成一张功能愿望清单：

### 1. 必要联动

不处理就会使当前功能逻辑错误、数据断链、权限失真、历史不可解释或下游失去口径。必须进入本次设计；如果是当前功能成立的必要条件，默认进入实施范围。若成本或不可逆性显著增加，先说明并请求一次确认。

### 2. 价值扩展

能明显提高使用价值，但当前功能即使没有它也能独立成立。主动提出价值与代价，未经用户确认不实施。

### 3. 远期机会

可能成为未来产品能力，但缺乏当前证据或与本轮目标距离较远。只写入候选或收口记录，不在当前对话中继续展开。

广思考不等于自动建设。设计视野可以覆盖整个系统，代码、数据迁移和外部动作只执行“必要且已确认”的范围。

## 面向人使用时转译界面

如果交付物是应用、网页、工作台、表格、操作型课件或其他需要人持续操作、判断、录入的成品，读取 [interface-translation.md](interface-translation.md)。先把规划主线转成连续任务、页面状态和界面合同，再进入视觉和开发。

认知助手只负责决定“界面必须怎样承接工作”，不扩张成通用视觉设计系统。具体组件、CSS、图表或文件格式仍由对应实现能力完成。

## 共同定义与渐进开工

如果目的只能由系统推断、存在多种可行形态、工作返工成本高或用户已经多次纠正，实施前读取 [collaborative-definition.md](collaborative-definition.md)。先让用户看见目的归属、组件合同、候选方案与推荐、低保真流程、代表性样板计划和验收标准，再按确认强度逐步进入样板和完整实现。

这不是把所有任务变成开会。明确、机械、低风险的改变可以直接做；已由用户原话明确的目的和边界无需重复确认。对中高风险代码任务，用 `scripts/project_index.py gate` 检查是否可以进入 `sample` 或 `full` 阶段。

## 面向用户的设计变化单

系统变更方案至少形成下面这组结果；简单项可以合并表达，但不能丢失边界：

```text
最终现实结果：用户为什么做这件事
当前交付物合同：负责什么、不负责什么、真实规则、完成证据
原始设计逻辑：父系统目标、当前组件角色、事实真源
本次需求：用户要改变的业务结果
保持不变：原有不变量与不可破坏的口径
发生变化：对象、角色、状态或链路的变化
必要上下游联动：当前功能成立所必需的联动
下一步承接：现在只准备什么输出，不建设什么下游
主动发现但暂不实施：价值扩展与远期机会
本轮最终实施范围：明确做什么、不做什么、如何验收
```

不要只复述用户刚说的字段或页面；至少给出一个由系统关系推导出的必要联动。如果没有必要联动，也要说明扫描过哪些相邻层以及为何独立成立。

## 实施与验收

实施前先确认“设计范围”和“代码范围”没有混淆；中高风险任务还要通过共同定义闸门。实施中如发现新的必要联动，先判断属于技术补全还是语义变化：前者可在边界内继续，后者更新原变化单并暂停扩大代码。完成时同时检查：

- 当前实现是否仍服务于规划主线，而不是只满足最近一句话；
- 用户纠正是否已经传播到所有受影响位置，被否定路线是否真正移除；
- 横向角色闭环是否成立；
- 纵向数据闭环是否成立；
- 是否出现无人维护的配置、无人使用的输入、无法解释的指标；
- 个人视图、管理视图和下游口径是否来自同一事实；
- 停用、删除、历史引用、未知值和纠错路径是否可解释；
- 价值扩展与远期机会是否仍被隔离在未实施范围。
- 面向人使用的成品是否已经通过界面合同与一个真实任务样本的连续预演。

## 回归样例

### 获客与培训协同

新增“获客与培训”不能只落成字段、页面和导入。扫描必须发现：管理员与业务员/销售的不同视图；一个员工可能绑定多个微信的归因关系；渠道、人员等配置的停用、删除与历史引用；个人承接与管理汇总；经营观测组件的只读下游协议。界面美化、智能建议等可作为价值扩展，不因本次需求自动实施。

### 新增任务状态

不能只新增枚举。至少检查状态由谁产生、谁能修改、个人与管理视图如何解释、历史记录是否保留，以及外部同步与报表是否需要同口径更新。

### 接入新数据源

不能只写连接器。至少检查事实真源、只读或可写边界、日期与时区语义、未知值和重复值处理、归属规则，以及下游看板是否会把“没有数据”误判为“业务为零”。

### 成本表服务上架

最终目标可以是快速上架，但当前成本表的职责可能只包括识别产品、选择固定组合或设计 SKU、计算成本与定价。图片上传、平台发布和链接任务属于下游，不应因此自动进入成本表；当前只需输出下游可稳定使用的产品、SKU、成本和建议售价。

### 课程转操作工具

“帮助没听过课程的人学会”不能默认做成原文、摘要、术语说明和多个独立计算器。先判断真实结果是否是完成一套操作；若是，应从状态变化、通关条件、失败退路和上下步数据承接推导交付形态，再决定使用地图、向导、工作台或其他界面。
