# 系统一致性分支：广思考，窄执行

## 目的

当既有系统新增页面、模块、字段、角色、状态或数据源时，不把用户刚提到的局部需求直接翻译成代码。先恢复父系统的原始目标和当前业务闭环，主动识别局部变化必然牵动的上下游，再把设计范围与本轮实施范围分开。

这不是第五个工作流，而是 `expansion_gate` 在既有系统变更场景中的一个分支。

## 触发信号

满足任意一项时进入本分支：

- 既有系统新增模块、页面、字段、状态、角色、权限或数据源；
- 一个局部变化同时影响角色、配置、数据、状态、视图、协议或历史数据中的三层以上；
- 一个任务横跨多个仓库、应用或业务组件；
- 用户要求“形成闭环”“上下联动”“保持原来的设计逻辑”或“主动多想一点”；
- 当前实现虽然满足字面需求，却可能产生孤立配置、孤立表单、孤立指标或无人承接的数据。

纯机械修改、独立文案调整和不改变业务语义的小修不进入本分支。

## 先恢复设计宪法

按以下优先级取得最小充分背景，不要求用户重填需求：

1. 当前用户原话、明确纠正与已确认边界；
2. 父系统的 `PRODUCT.md`、产品原则、业务协议与关键设计文档；
3. 项目索引中的父系统、组件角色、上下游与事实真源；
4. 当前实现、真实数据结构、权限与已有结果；
5. 相关历史任务中的稳定决定。

如果文档与现实实现冲突，把冲突显式列为待决定项；不要默认为文档或代码任何一方天然正确。

先用一句话分别回答：

- 父系统最终帮助谁完成什么经营动作？
- 当前组件在父系统里负责生产事实、加工事实、汇总观察，还是执行动作？
- 哪个组件或外部系统是每类关键事实的真源？
- 本次局部需求改变了哪条业务链路，而不只是改了哪个页面？

## 双向扫描

### 横向角色闭环

沿同一业务时点检查：

- 谁配置规则或基础资料；
- 谁录入、执行或修正；
- 谁拥有客户、任务或结果；
- 谁查看个人结果；
- 谁做管理判断、纠偏与复盘；
- 不同角色是否看到同一事实的合适切面，而不是复制同一页面。

### 纵向数据闭环

沿事实生命周期检查：

```text
配置/主数据 → 一线输入 → 归属与状态 → 业务结果
→ 个人视图 → 管理视图 → 下游观测/报告 → 复盘与纠正
```

至少扫描这些传播层；只展开与本次需求有关的层：

- 主数据与配置生命周期：新增、停用、删除、历史引用；
- 角色、权限与可见范围；
- 录入入口、移动端与批量导入；
- 领域对象、状态流转与时间语义；
- 所有权、来源与业绩归因；
- 个人工作视图与个人结果；
- 管理汇总、异常与纠偏动作；
- 下游协议、报表和观测口径；
- 历史数据、迁移、未知值与人工修正。

## 主动扩展分级

发现的联动必须分为三层，不得混成一张功能愿望清单：

### 1. 必要联动

不处理就会使当前功能逻辑错误、数据断链、权限失真、历史不可解释或下游失去口径。必须进入本次设计；如果是当前功能成立的必要条件，默认进入实施范围。若成本或不可逆性显著增加，先说明并请求一次确认。

### 2. 价值扩展

能明显提高使用价值，但当前功能即使没有它也能独立成立。主动提出价值与代价，未经用户确认不实施。

### 3. 远期机会

可能成为未来产品能力，但缺乏当前证据或与本轮目标距离较远。只写入候选或收口记录，不在当前对话中继续展开。

广思考不等于自动建设。设计视野可以覆盖整个系统，代码、数据迁移和外部动作只执行“必要且已确认”的范围。

## 面向用户的设计变化单

系统变更方案至少形成下面这组结果；简单项可以合并表达，但不能丢失边界：

```text
原始设计逻辑：父系统目标、当前组件角色、事实真源
本次需求：用户要改变的业务结果
保持不变：原有不变量与不可破坏的口径
发生变化：对象、角色、状态或链路的变化
必要上下游联动：当前功能成立所必需的联动
主动发现但暂不实施：价值扩展与远期机会
本轮最终实施范围：明确做什么、不做什么、如何验收
```

不要只复述用户刚说的字段或页面；至少给出一个由系统关系推导出的必要联动。如果没有必要联动，也要说明扫描过哪些相邻层以及为何独立成立。

## 实施与验收

实施前先确认“设计范围”和“代码范围”没有混淆。实施中如发现新的必要联动，更新原变化单；不要悄悄扩大代码。完成时同时检查：

- 横向角色闭环是否成立；
- 纵向数据闭环是否成立；
- 是否出现无人维护的配置、无人使用的输入、无法解释的指标；
- 个人视图、管理视图和下游口径是否来自同一事实；
- 停用、删除、历史引用、未知值和纠错路径是否可解释；
- 价值扩展与远期机会是否仍被隔离在未实施范围。

## 回归样例

### 获客与培训协同

新增“获客与培训”不能只落成字段、页面和导入。扫描必须发现：管理员与业务员/销售的不同视图；一个员工可能绑定多个微信的归因关系；渠道、人员等配置的停用、删除与历史引用；个人承接与管理汇总；经营观测组件的只读下游协议。界面美化、智能建议等可作为价值扩展，不因本次需求自动实施。

### 新增任务状态

不能只新增枚举。至少检查状态由谁产生、谁能修改、个人与管理视图如何解释、历史记录是否保留，以及外部同步与报表是否需要同口径更新。

### 接入新数据源

不能只写连接器。至少检查事实真源、只读或可写边界、日期与时区语义、未知值和重复值处理、归属规则，以及下游看板是否会把“没有数据”误判为“业务为零”。
