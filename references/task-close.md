# 任务收口

## 目标与触发

重要阶段已有结果或可复用决定时主动收口，不等用户提醒，也不等整个项目结束。普通进度、简单任务直接交付，不新建收口单。

## 必须保留的结论

读原目标、纠正、最终产物和验证。分别标出事实、用户判断、系统推断、未验证假设；保留被否决路线与原因，避免重提。只保存影响未来行动的决定及召回条件，不复制整段聊天或已有文档。

吸收外部方法时，明确它解决当前哪项问题，并落到本 Skill 的对应能力；不保留第二入口、来源包或原文副本作为运行依赖。使用适用场景验证，不以“还可研究”为由无限推迟交付。

## 知识收尾与行动交接

阶段成果改变项目事实、工程约定或后续使用方式时，执行 [知识收尾](knowledge-closeout.md)；用户单独要求文档/规则/记忆对齐时也使用该步骤。它负责知识面一致性，本文件负责阶段决定与召回；只有一个 `task_close`，不另造洁癖模式、日志系统或收口事件。

顺序是：实际成果与本轮差异 → 定位受影响知识面 → 按事实与权限修正 → 验证链接、命令和同源关系 → 更新必要的既有事件/索引 → 交付。收尾期间变更了文档或状态文件，工程检查和经授权的同步必须基于最终字节重新核对，不能拿收尾前的提交证明之后的修改已保存。

只对当前作用域得出结论；文档已对齐不代表已部署，平台生成记忆不可写也不阻断已经完成的文档交付。清场预览与删除分离：先汇报可复核成果并保留现场，取得汇报后的明确确认才执行破坏性清理。没有清场对象无需多问一次。

## 三类完成不能混用

- L1 工程证据：代码、静态检查、测试或构建。
- L2 场景证据：忠实数据完整模拟用户任务。
- L3 现实证据：真实设备、账号、业务或生产环境完成。

同时区分功能结果、Git 可恢复检查点、真实使用接受。代码任务读取工程检查，只有 `closure.ready=true` 且验收通过才称工程已收口；不能提交则保留功能成果，写具体阻碍。测试通过不覆盖用户“不好用”的反馈，也不因一处不满意抹掉其他成立结果。

系统变更核对必要横纵联动、纠正传播及未确认扩展仍在边界外；面向人的成品核对连续任务、主动作、完成和恢复。共同定义或样板接受不代表产品整体有用。

项目工程约定有变化时，还要核对“已确定／已实现／已验证”的实际落点、项目入口是否合并到正确文件、共享使用方是否同步。设计完成不冒充开发完成，工程选择状态不冒充用户确认；后续 Agent 继承情况需实际调用证据，入口文件存在只证明文件已交付。

## 最终答复

默认交结果、采用决定和影响使用的事项。完整收口可包含目标、确认事实、用户判断、采取决定、否决路线、召回条件、采用落点、证据和工程状态。不强制显示不适用字段或不相关的“还没做”。

只有用户询问方法或某认知动作确实改变关键选择时，附二至四条“方法→可核对证据→改变的决定”；这是可见决策依据，不要求输出内部思维链。没有改变决定不列能力覆盖率。

## 记录与同步

同一项目/问题/阶段只保留一个 task_close；后续实现、验证、提交、回归、采用结果更新原事件。跨阶段不同问题可以新建关联事件，线程相同不等于问题相同。

事件 closed 必须有可观察 outcome；仅作决定则写“决定已确认，效果尚未验证”，不留空。历史缺口按兼容规则保留，不猜填。

状态确有变化且同步授权有效时，按 cloud-sync.md 操作。源 Skill 与状态仓库分别核对；私有状态同步成功不能代表 Skill 源码也推送成功。无变化不造提交。
