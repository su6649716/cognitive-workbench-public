# 架构基线与持续施工

新建、新增模块、重构或跨模块修改时按需使用。独立小修只核对相关边界，不增加工作流或审批。

## 从当前目标定结构

全新建设从当前目标、规模、运行环境和真实外部约束设计，不默认承接旧架构、目录、技术栈或历史接口。维护任务才核实现行结构与必要兼容责任；原型转生产也需重新检验结构适用性。不能把“已有架构文档”无条件视为权威。

按 [项目工程规范](project-baseline.md) 选定具体做法，统一记入本项目基线。缺少独立维护理由时，不再创建第二份架构说明。“大厂结构”“前后端分离”“优雅”指职责清楚、变更有归属、易定位维护，不自动要求微服务、分仓或固定框架。

说明模块职责/位置、允许依赖、公共接口、展示与交互、业务与请求、接口与服务、数据存取与外部接入的归属。关键字段、错误、状态和配置保持一个真源，明确开发/运行/验证入口。按真实规模分层，不造空目录。

文档路径和验证提交按授权进入项目索引；核心不变量可进规划基线，不复制整篇文档。展开完整实现前，用代表流程验证各层连接；关键语义取舍仍由共同定义负责。

## 实施与维护

修改前确定功能归属、实际接口消费者、数据责任和验证范围。检查页面夹带存储/服务商细节、业务规则复制、跨模块改内部状态、循环依赖；改动散落时先查职责与接口，不用文件数量判断质量。

共用能力依据真实重复和稳定语义提取。新模块复用本项目选定的公共定义；引入历史代码须确认它适合当前架构，不能连带引入过期假设。一个文件职责混杂才拆，不靠行数证明质量。

全新实现验证当前合同，不把旧行为逐项复刻当验收。明确要求保持行为的重构，则先保留相应行为证据，分阶段迁移并验证实际承接对象。不可逆数据变化另需恢复方案；Git 回退不等于数据恢复。

## 验收

功能满足当前目标，职责一致、逻辑可测、错误可定位、替换外部服务影响明确；公共规则变化同步相关实现和文档。验收只覆盖真实职责，不添加未要求的旧版兼容工程。完成后按 [工程基线](engineering-baseline.md) 检查本轮 Git 起点和收口。
